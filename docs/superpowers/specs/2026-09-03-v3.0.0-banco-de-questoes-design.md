# Trilha Integrar — v3.0.0 (banco de questões)

**Data:** 2026-09-03
**Tipo:** Breaking change (major)
**Status:** design aprovado — aguardando plano de implementação

## Sumário

A v3.0.0 é o repositionamento do produto: de **questionário** (listas fechadas de simulados percorridas em ordem, atalhadas por uma home colorida com matriz ano × área) para **banco de questões** (repositório consultável e persistido no Postgres). A identidade visual fica mais sóbria (branco/preto/cinza + accents em vermelho/vinho inspirados no logo). A home é reformulada com 3 CTAs. Duas features novas entram: **trilhas de estudo** curadas com fluxo de aprovação e **geração de PDF para impressão** restrita a professor. A navegação sai de 7 abas para 4 fixas. Cadastro obrigatório — não há mais uso anônimo.

## Motivação

O app hoje trata cada simulado ENEM como uma entidade fechada (32 JSONs estáticos em `public/`, um por ano/área, percorridos linearmente pelo aluno). Isso limita a experiência a "abrir simulado e responder" e não aproveita o volume de conteúdo que já existe (~1440 questões ENEM + listas de professores).

Repositando como **banco de questões**, cada questão vira uma unidade endereçável e filtrável — o aluno monta a própria sessão por busca, sorteio ou trilha curada. O produto passa a suportar padrões de uso que hoje são impossíveis (estudar 5 questões de "genética" enquanto espera o ônibus, refazer só o que errou, seguir uma trilha temática montada pelo professor).

Também é o momento certo pra:
- Consolidar a identidade visual (5 favicons coloridos + matriz colorida do EnemPicker vão embora).
- Simplificar a navegação (7 abas → 4).
- Aposentar features que não pegaram sem fricção (guest anônimo, aba Pesquise atual como catálogo passivo).
- Migrar questões pra DB — pré-requisito de qualquer futuro dashboard, estatística ou revisão espaçada (v3.1+).

## Posicionamento

- **Antes (v2.x):** questionário → responder simulados fechados.
- **Depois (v3.0.0):** banco de questões → montar sessões próprias a partir de um repositório indexado.

## Modelo de acesso

Três roles, todos já existem no código (`user.role`), a novidade é formalizar no schema:

| Role | Cria | Vê |
|---|---|---|
| `user` (default) | Trilhas (nascem pendentes) | 4 abas |
| `prof` | Trilhas (auto-aprovadas), listas (`question_sets`) | 4 abas + Escrever + Imprimir + aprovações |
| `admin` | Tudo de `prof` + promove `user` → `prof` | Tudo + painel Administre |

> **Nota terminológica:** o role name no banco é `user` (herdado do estado atual). Em prose, "aluno" e "user" referem-se à mesma coisa — usamos o termo em português quando falamos da pessoa e o identificador do enum quando falamos do código.

**Fluxo de auth:**
- Cadastro público (`POST /api/auth/register`) cria `role='user'` explicitamente.
- Admin promove `user` ↔ `prof` no painel de administração (endpoint `PATCH /api/admin/set-role` e UI toggle em App.jsx já existem em produção — v3 apenas formaliza o schema).
- Guest cai em tela de login/cadastro — **não há uso sem sessão**.
- JWT continua carregando `{ userId, username, role }` como já faz.

## Arquitetura de dados

### Tabelas novas

**`multiple_choice_questions`** — banco unificado de questões. Nome reflete que a tabela suporta qualquer questão de múltipla escolha, não só ENEM.

```sql
CREATE TABLE multiple_choice_questions (
  id            SERIAL PRIMARY KEY,

  source        TEXT NOT NULL,             -- 'enem' | 'teacher_list' | 'custom'
  source_list   TEXT,                      -- ex: 'ricardo_lista1' (só p/ teacher_list)
  area          TEXT,                      -- 'math' | 'nature' | 'humanas' | 'linguagens'
  test          TEXT,                      -- 'ENEM' etc.
  year          INTEGER,
  number        INTEGER NOT NULL,

  text          TEXT NOT NULL,
  alternatives  JSONB NOT NULL,            -- {a, b, c, d, e} — suporta N alternativas
  answer        TEXT NOT NULL,             -- 'a'..'e' (ou letra correspondente)
  images        TEXT[] DEFAULT '{}',
  tags          TEXT[] DEFAULT '{}',
  disciplinas   TEXT[] DEFAULT '{}',
  difficulty    INTEGER,                   -- 1..10, nullable
  context_key   TEXT,                      -- FK textual p/ contexts.json enquanto não migra

  review        BOOLEAN DEFAULT FALSE,

  created_at    TIMESTAMPTZ DEFAULT NOW(),
  updated_at    TIMESTAMPTZ DEFAULT NOW(),

  UNIQUE (source, source_list, area, test, year, number)
);

CREATE INDEX idx_mcq_area          ON multiple_choice_questions(area);
CREATE INDEX idx_mcq_year          ON multiple_choice_questions(year);
CREATE INDEX idx_mcq_source        ON multiple_choice_questions(source);
CREATE INDEX idx_mcq_tags          ON multiple_choice_questions USING GIN(tags);
CREATE INDEX idx_mcq_disciplinas   ON multiple_choice_questions USING GIN(disciplinas);
```

**`contexts`** — segunda leva (task #9), depois da tabela `multiple_choice_questions` estar populada.

```sql
CREATE TABLE contexts (
  key       TEXT PRIMARY KEY,   -- ex: "ctx_q152_2024"
  text      TEXT NOT NULL,
  images    TEXT[] DEFAULT '{}',
  title     TEXT
);
```

`multiple_choice_questions.context_key` passa a resolver contra essa tabela em vez do JSON.

**`trilhas`** — trilhas de estudo.

```sql
CREATE TABLE trilhas (
  id            SERIAL PRIMARY KEY,
  name          TEXT NOT NULL,
  description   TEXT,
  tags          TEXT[] DEFAULT '{}',       -- se derivada por filtro de tags
  question_ids  INTEGER[] DEFAULT '{}',    -- se curada manualmente (ordem preservada)
  source_kind   TEXT NOT NULL,             -- 'tags' | 'manual'
  status        TEXT NOT NULL DEFAULT 'pending',  -- 'pending' | 'approved' | 'rejected'
  created_by    INTEGER REFERENCES users(id) ON DELETE SET NULL,
  approved_by   INTEGER REFERENCES users(id) ON DELETE SET NULL,
  approved_at   TIMESTAMPTZ,
  created_at    TIMESTAMPTZ DEFAULT NOW()
);

CREATE INDEX idx_trilhas_status ON trilhas(status);
```

Regra de ordem no consumo: se `source_kind='manual'`, front respeita `question_ids` na ordem salva; se `source_kind='tags'`, back sorteia questões que casam com `tags` e o front trata a ordem como aleatória fixa por sessão (chave da sessão inclui `trilha_id` + timestamp de início).

**`trilha_progress`** — progresso persistido do aluno numa trilha.

```sql
CREATE TABLE trilha_progress (
  id                    SERIAL PRIMARY KEY,
  user_id               INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  trilha_id             INTEGER NOT NULL REFERENCES trilhas(id) ON DELETE CASCADE,
  question_ids_answered INTEGER[] DEFAULT '{}',
  last_seen_at          TIMESTAMPTZ DEFAULT NOW(),
  UNIQUE (user_id, trilha_id)
);
```

### Tabelas alteradas

**`users`** — enum `user_role` e coluna `role` **já existem** em produção (criadas direto no console da Neon em algum momento, sem migration) mas não no schema versionado. Migration nova incorpora, idempotente:

```sql
-- 009_add_users_role.sql
DO $$
BEGIN
  IF NOT EXISTS (SELECT 1 FROM pg_type WHERE typname = 'user_role') THEN
    CREATE TYPE user_role AS ENUM ('user', 'prof', 'admin');
  END IF;
END $$;

ALTER TABLE users
  ADD COLUMN IF NOT EXISTS role user_role NOT NULL DEFAULT 'user';
```

`api/auth/register.js` passa a setar `role='user'` explicitamente em vez de depender do default.

### Tabelas mantidas sem alteração

`test_results`, `feedback`, `daily_challenges`, `daily_challenge_results`, `explanations`, `question_sets`. Explicações continuam com chave `(area, year, test, number)` e o front resolve o lookup contra o banco novo mantendo essa mesma chave.

### JSONs

- Todos os JSONs em `public/` **ficam preservados** para auditoria após a migração — nenhuma remoção nessa versão.
- Fonte de verdade passa a ser o DB; JSONs viram read-only.

## Navegação e telas

### Estrutura geral

```
Sem sessão → Login / Cadastro
Com sessão → Home (3 CTAs) → aba escolhida (4 abas persistentes no topo)
```

Header persistente em toda tela logada:
- Esquerda: logo Integrar + nome do app.
- Direita: [caderno] (painel lateral sob demanda) + [avatar do usuário].
- Menu do avatar: "Meu perfil" · "Tema claro/escuro" · "Sair" · [pra prof/admin] atalhos "Escrever Questões", "Imprimir Lista", "Trilhas pendentes".

### Home

Tela de boas-vindas visível ao entrar. **Acima** das 4 abas (não é uma aba).

- Título de boas-vindas.
- 3 cards grandes lado a lado com ícone + rótulo + descrição curta:
  1. **Responder Questões** → aba Responder Questões.
  2. **Escrever Questões** → tela separada de professor (só visível se `role in ('prof','admin')`).
  3. **Gerar Lista para Impressão** → aba Imprimir Lista (só visível pra professor).

Aluno vê 1 card (Responder). Professor vê os 3.

### Aba Jogos

Sub-itens:
- **Show do Milhão** — feature existente, refactor visual apenas.
- **Desafio Diário** — feature existente (`daily_challenges`), migrada da estrutura antiga.

### Aba Pesquisar Questões

UI de busca similar à existente na criação de listas de professor (reaproveitamento). Aluno filtra por área, tags, dificuldade, ano — recebe a lista de questões e pode iniciar sessão a partir do resultado.

### Aba Responder Questões

Três sub-modos (cards lado a lado no estilo da home, um nível abaixo):
- **Prova Completa** — formulário simples: área (radio) + ano (dropdown) → inicia sessão de 45 questões (ou N da prova).
- **Sorteio** — quantidade (5/10/20) + área (todas/math/nature/linguagens/humanas) → inicia sessão sorteada.
- **Trilhas** — lista de trilhas aprovadas. Se `role in ('prof','admin')`, seção "Pendentes de aprovação" aparece no topo com botões Aprovar/Rejeitar. Aba "Responder Questões" ganha badge com contador de pendências.

Ao entrar numa trilha, aluno vê progresso ("12 de 20 respondidas") e "Retomar" ou "Reiniciar".

### Aba Imprimir Lista

Visível só pra professor. Formulário de filtros (área, tags, ano, dificuldade, quantidade) + botão "Gerar PDF". Baixa dois arquivos: a prova (sem gabarito) e o gabarito (arquivo separado). Layout com logo Integrar no cabeçalho.

### Tela "Escrever Questões" (fora das abas)

Reaproveita `QuestionEditor.jsx` existente sem mudança funcional — apenas refactor visual com a nova identidade. Continua criando `question_sets` (não escreve direto em `multiple_choice_questions` nessa versão).

### Painel do admin

Existe mas escondido do fluxo comum. Acessível via menu do avatar para `role='admin'`. Ganha nova sub-área: **"Promover usuário"** — lista de alunos com botão "Tornar professor".

## Features novas em detalhe

### Trilhas de estudo

**Criação:** qualquer usuário logado pode criar. Formulário: nome, descrição, escolha de fonte (`tags` ou `manual`), lista de tags OU seleção manual de question_ids (usando a UI de Pesquisar Questões).

**Estado inicial:** `status='pending'` — invisível para outros usuários até aprovação. **Toda trilha nasce pendente**, incluindo as criadas por `prof` e `admin` — a decisão do usuário foi "qualquer um cria, mas para aparecer precisa de aprovação de um professor", e nada foi dito sobre auto-aprovação. Se isso virar atrito na prática, a v3.1 pode adicionar auto-approve para prof.

**Aprovação:** professor vê seção "Pendentes de aprovação" no topo da aba Responder Questões / Trilhas. Cada trilha pendente tem preview (nome, criador, fonte, número de questões). Botões Aprovar / Rejeitar. Ao aprovar, `approved_by` e `approved_at` são setados.

**Consumo pelo aluno:** clica na trilha → vê barra de progresso → botão "Iniciar" ou "Retomar". Ordem das questões: `source_kind='manual'` respeita `question_ids`; `source_kind='tags'` é aleatória fixa por sessão. Progresso persistido em `trilha_progress` a cada resposta.

### Geração de PDF para impressão

**Trigger:** aluno de `role='prof'` ou `'admin'` clica no CTA "Gerar Lista para Impressão" na home ou na aba Imprimir Lista.

**Formulário:** filtros (área, tags, ano, dificuldade, quantidade). Nome da lista opcional. Botão "Gerar PDF".

**Saída:** dois arquivos baixados:
- `lista-<slug>-questoes.pdf` — enunciados + alternativas, sem gabarito.
- `lista-<slug>-gabarito.pdf` — só o gabarito com número + letra.

**Layout:** logo Integrar no cabeçalho, título da lista, questões numeradas, rodapé com paginação. Espaço para o aluno marcar a resposta ao lado de cada questão (bolinhas a/b/c/d/e). Detalhes de tipografia e espaçamento ficam pra fase de implementação.

**Tecnologia (a decidir na implementação):**
- `@react-pdf/renderer` — client-side, sem dependência de servidor.
- `pdfmake` — client-side, mais controle de layout.
- Puppeteer/Chromium serverless — server-side, renderiza HTML como no app (KaTeX + imagens funcionam nativamente).

Recomendação preliminar: puppeteer serverless na Vercel, para reaproveitar o rendering existente (KaTeX, imagens), evitar duplicar templates entre app e PDF. A escolha final fica pra fase de implementação.

4. **Task #3** — API de leitura do banco unificado. Endpoints: `GET /api/questions/search`, `GET /api/questions/random`, `GET /api/questions/prova`, `GET /api/questions/by-trilha/:id`. Contexts resolvidos via join com `contexts`.

9. **Task #7** — Geração de PDF (decisão de tecnologia + implementação + gabarito separado).

## Riscos e questões abertas

- **Tecnologia de PDF** (task #7) — decisão adiada pra implementação. Se puppeteer serverless não couber no plano da Vercel (cold start, tamanho), fallback é `@react-pdf/renderer` client-side com KaTeX pré-renderizado como SVG.
- **`context_key` intermediário** — enquanto contexts não migra (task #9), o front resolve `context_key` lendo `contexts.json`. É uma janela de tempo com dois lugares fonte de verdade — precisa ser bem sinalizado.
- **Ordem em trilhas por tags** (chave da sessão) — precisa definir de onde vem o seed. Sugestão: `hash(user_id + trilha_id + Math.floor(started_at / 86400))` — muda uma vez por dia. Detalhe pra implementação.
- **Aprovação inicial de trilhas pré-existentes** — se algum aluno criar trilhas antes de haver professores promovidos, elas ficam pendentes indefinidamente. Mitigação: admin já existe e pode aprovar.
- **Migração de listas de professor com formato heterogêneo** — a task #8 assume que todos os JSONs seguem o mesmo formato base. Se algum tiver estrutura destoante, pode ser preciso auditoria caso-a-caso. Considerar rodar o script em modo dry-run primeiro.
- **Comportamento do daily_challenge dentro de "Jogos"** — a interação atual é home → daily challenge; agora vira aba Jogos → sub-item. O onboarding do hábito pode ser afetado. Pode valer um pequeno indicador no menu do avatar ("Desafio de hoje ainda pendente").
